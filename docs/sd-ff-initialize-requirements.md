# 全エリアSD FF初期化の要件・仕様（移植元ソース調査）

調査日：2026年10月27日

第1〜8節は移植元SDDirectAXSと移植前の状態の調査記録、第9節はその後に合意して実装した移植先の仕様です。利用者の指定により、CSVに定義された先頭32KiBも初期化対象に含めます。実機SDの初期化は行わず、模擬SDと画面処理の自動テストで検証しています。

## 1. 目的と初期化範囲

選択したSDカードの、CSVで定義された各領域を **全バイト `0xFF`** に書き換えます。`0x00`での消去やファイルシステムのフォーマットではありません。

- 「全エリア」は、CSVの終端`E`より前に定義された全領域を意味します。SDカード全容量を一律に埋める処理ではありません。
- `A`・`R`・`W`・`N`・`0`などのフラグによる選別はありません。未知のフラグも`E`でなければ処理する構造です。
- PC上の対応ファイルがなくても初期化します。ファイルの内容やサイズも使用しません。
- CSVにない領域・領域間の隙間・最終領域より後ろには書き込みません。
- カード種別は初期化するデータに影響しません。`FILE-BA.001`も、他の行と同じく定義領域全体を`0xFF`にします。
- CSVの先頭行から順に処理します。アドレスによる並べ替えや連続領域の結合は行いません。

根拠：移植元`SDDirectAXSDlg.cpp:918–955, 965–977, 1019–1045`。

## 2. ボタン押下からの呼び出し経路

```text
「全エリアSD FF初期化」(IDC_BUTTON5)
  → OnButton5()
  → fopen("sdDirectaxs.csv", "r")
  → ParameterAndSDCardOpen(FP, &hFile)
  → 成功時のみ FilereadSetToSD(PARAMETER_ALLFF, FP, hFile)
  → UpdateData(FALSE)
```

`PARAMETER_ALLFF`は`0x33`です。CSV解析は書き込みモード`SDWRITEMODE = 1`で行います。SD書き込みボタンと同じ関数を、処理モードを変えて呼び出しています。

根拠：移植元`SDDirectAXS.rc:106`、`SDDirectAXSDlg.cpp:22, 28, 121, 474–494, 903–918`。

## 3. 実行条件とSDの開き方

1. 起動時に`GetLogicalDrives()`で列挙し、`DRIVE_REMOVABLE`のドライブを選択欄へ追加します。初期値は`--`です。
2. ボタン押下時に、カレントディレクトリー相対の`sdDirectaxs.csv`を読み直します。
3. ドライブ未選択、CSVオープン失敗の場合は開始しません。
4. 選択した論理ドライブ`\\.\X:`を読み書き権限で開き、`IOCTL_STORAGE_GET_DEVICE_NUMBER`で物理ドライブ番号を取得します。
5. 論理ドライブを閉じて、`\\.\PhysicalDriveN`を読み書き権限・読み書き共有で開き直します。

CSVのアドレスは **物理ドライブ先頭からのバイト位置** です。パーティションの開始位置は加算しません。

旧実装には、実行確認画面、権限昇格、メディア容量検査、CSVの全行事前検査、ボリュームの排他ロックはありません。

根拠：移植元`SDDirectAXSDlg.cpp:167–192, 483–490, 664–762`。

## 4. アドレスと書き込み方法

通常行は`フラグ,ファイル名,開始アドレス,終了アドレス`の形式です。アドレスは16進数で、開始・終了の両端を含みます。

```text
領域サイズ = 終了アドレス − 開始アドレス ＋ 1
```

各領域について以下を実行します。

1. 状態欄に`ファイル名 + SD書き込み中`を表示します。FF初期化専用の表記はありません。
2. バッファ全体を`memset(..., 0xFF, ...)`で埋めます。入力ファイルからの`fread`はFF初期化モードでは実行しません。
3. `SetFilePointer`で領域の開始アドレスへ移動します。
4. `WriteFile`で512バイトずつ書き込みます。残量が512バイト未満なら、その残量だけ書きます。各書き込み後、バッファを再び`0xFF`で埋めます。
5. CSVの次の行へ進み、`E`で終了します。
6. CSVとSDのハンドルを閉じ、状態欄に「SD書き込み終了!!」を表示します。

旧実装は`WriteFile`の成功を確認するだけで、書き込みバイト数の一致、明示的なフラッシュ、読み戻し照合は行いません。「終了!!」は、全バイトの`0xFF`を読み戻して確認したという意味ではありません。

根拠：移植元`SDDirectAXSDlg.cpp:517–661, 920–922, 961–991, 1017–1049`。

## 5. CSVによる実際の範囲の違い

以下は調査時点のファイルを集計した値です。件数・範囲・総サイズは固定要件ではありません。

| CSV | 領域数 | 総初期化バイト数 | 最初の開始位置 | 最後の終了位置 |
| --- | ---: | ---: | --- | --- |
| 移植元`sdDirectaxs.csv` | 87 | 33,750,528 | `0x00008000` | `0x02037DFF` |
| 移植先`config/sdDirectaxs.csv` | 94 | 40,611,328 | `0x00000000` | `0x07BAFFFF` |

移植元CSVの87領域は連続しており、先頭32KiBは対象外です。

移植先の現行CSVには次の行があります。

```csv
A,FILE-00.001,00000000,00007FFF
```

旧実装と同じルールを現行CSVに適用すると、**物理ディスク先頭の32KiBも`0xFF`に書き換えます**。MBR形式のカードであれば、その位置にあるパーティション情報等も対象に含まれます。旧CSVと同じ「先頭を保持する処理」にはなりません。

現行CSVのフラグ内訳は`A:8`、`0:85`、`N:1`で、全94領域が対象になります。`0`や`N`であることを理由に保護されません。

また、現行CSVには次の未定義区間があります。これらを含めて先頭から最後まで連続して埋めると、旧実装の領域単位の動作と異なります。

```text
0x02037E00–0x02500DFF
0x02582E00–0x02583DFF
0x02883E00–0x078ABFFF
0x078AD000–0x078AFFFF
```

両CSVとも定義領域の開始位置・サイズは512バイト境界に整列しています。移植先では「SD書込」「全エリアSD読み込み」と同じCSV探索規則を使用し、選択された外部CSVを内蔵CSVより優先します。旧実装のカレントディレクトリー相対の探索とは異なります。

根拠：移植元`SDDirectAXSDlg.cpp:673–758, 961–964, 991–1015, 1047–1049`。

## 7. 旧実装の不具合・不足

- **不要な入力ファイルオープンと閉じ忘れ**：FFモードでも各行で`fopen(..., "rb")`しますが、ファイルの有無を判定せず、内容も読みません。`fclose(FPOUTPUT)`はファイル書き込みモードだけで実行されるため、FF初期化時にオープンできた入力ファイルは閉じられません。入力ファイルへの依存は移植すべき要件ではありません。
- **「選択エリア」との区別がない**：`PARAMETER_SELECTFF`でもフラグによる選別をせず、`E`までの全領域を初期化します。旧実装の「SD選択エリア FF初期化」は、対象範囲の判定に関して「全エリア」と同じです。
- **短い書き込みを見逃す**：`WriteFile`の戻り値だけを見て、実書込数`tempreadbyte`と要求数を比較しません。処理残量もAPI呼び出し前に減らします。
- **シークの失敗を見逃す**：`SetFilePointer`の戻り値を検査しません。
- **CSV・容量の検査不足**：EOF、終端欠落、不正アドレス、逆転、重複領域、SD容量外などを事前検査しません。アドレスは旧32ビットの型・APIで扱います。
- **ロック・照合がない**：SD使用中でも排他ロックせず開き、初期化後の全バイト照合や最終照合は行いません。
- **共通初期化処理の解放漏れ**：ドライブ未選択時にCSVを閉じず、物理番号取得失敗時には論理ドライブのハンドルを閉じない経路があります。

根拠：移植元`SDDirectAXSDlg.cpp:517–661, 673–676, 720–734, 925–955, 977–991, 1004–1041`。

## 8. 移植前の状態と既存APIの評価

調査時点の`src/components/SdMenu.vue`のボタンは、押下ログを出すだけで、SD初期化処理や進捗ポップアップには接続されていませんでした。その後、第9節のとおり移植しました。

バックエンドには、管理者プロセス経由の`sd_fill`と`sd_verify_fill`があります。ただし、そのまま全領域初期化の完成済み部品として扱うことはできません。

| 既存部品 | 調査で確認した制約 |
| --- | --- |
| `windows_api::sd_fill` | 1領域用。呼び出しごとにハンドルを開く。512バイト固定でサイズを切り上げるため、非整列領域では末尾の対象外データも書き換える。ロックに失敗しても処理を継続する構造。ゼロ書込でループを抜け、要求数未満の結果を返す場合がある |
| 同APIのバッファ | `FILE_FLAG_NO_BUFFERING`を指定する一方、通常の`Vec`を使用し、バッファのセクター境界への整列は保証していない |
| `windows_api::sd_verify_fill` | 不一致バイト数を返す。要求サイズを読み切ったかの検査がなく、0バイト・部分読込で早期終了しても不一致0を返し得る。通常のキャッシュ付き読み取りで、書込の確定・再読込保証とは分けて検討が必要 |
| `sd_batch` / `BatchDisk` | 既存SD書込の一括処理。単一ハンドル、必須ロック、整列済みバッファ、領域端の対象外バイト保持、フラッシュ、独立バッファによる全バイト照合を再利用する候補 |

入力ファイルを選別する`sd_batch::prepare`や、入力ファイルを開いて固定する`execute`は、FF初期化の対象決定へそのまま流用できません。CSV全行からの領域計画を作り、ファイルを開かず`0xFF`を生成する経路が必要です。書込・照合の低レベル処理と、GUIのポップアップ・管理者プロセス・操作制限は共通化できる候補です。

根拠：移植先`src/components/SdMenu.vue`、`src-tauri/src/lib.rs`の`sd_fill`/`sd_verify_fill`、`sd_worker.rs`の`Operation::Fill`/`VerifyFill`、`windows_api.rs:730–987`、`sd_batch.rs`の`prepare`/`expected`/`transfer_phases`/`execute`。

## 9. 移植先の確定仕様と実装

1. **範囲**：CSVの`E`より前の全領域を対象とし、フラグ・入力ファイルの有無を無視する。CSV順で初期化し、CSVの範囲外と隙間は保持する。**利用者の指定により、現行CSVの先頭32KiBも初期化する**。その範囲にあるパーティション情報等も上書きする。
2. **CSV・事前検査**：既存SD書込と同じ探索規則でCSVを読み、終端`E`、アドレス、逆転、領域重複、SD容量内であること、実行ID、対象0件を検査する。exeが対象SDと同じ物理ディスクにある場合は拒否する。管理者プロセスでも同じ計画を再作成し、GUI側の計画と異なる場合は書き込まず停止する。
3. **実行前表示**：ボタン押下時に`panel_text`へ操作ログを追加し、共通の進捗ポップアップを表示する。ドライブ、CSVに含まれる先頭32KiBも対象であること、初期化と2回の照合を行うことをログに表示する。対象確定後に領域数・合計バイト数・総処理量も表示する。SD書込と同様、確認一覧や追加確認操作を挟まず、事前検査成功後に開始する。
4. **進捗・件数**：「FF初期化中」「照合中」「最終照合中」などの段階、対象名、件数、進捗率、所要時間、ログ、結果を表示する。進捗率の分母は領域サイズ合計の3倍、完了件数は最終照合済み領域数とする。初期化・直後照合が終わっただけでは完了件数を加算しない。
5. **処理と正常完了条件**：必須のボリュームロック、単一の物理SDハンドル、最大4MiBの整列済みI/O、独立した書込・読込・期待値バッファを使う。非整列領域の端では対象外バイトを保持する。各領域の初期化・フラッシュ・全バイト照合後、全領域を再読込して最終照合する。先頭領域の書換え後もドライブ文字から再オープンせず、同じハンドルで処理する。全照合成功とハンドル解放後にのみ正常完了を通知する。
6. **異常時・操作制限**：不正CSV・容量外・ロック失敗は書込前に停止し、途中の書込・読込・照合失敗は後続を停止する。書換え済みの内容は元に戻さない。実行中のドライブ変更・ドロップ・F5・終了・ポップアップを閉じる操作を禁止する。途中キャンセルは設けず、完了・失敗後のログは保持する。

実装経路は`SdMenu.requestInitialize` → `HomeView.onSdFfInitialize` → `run_sd_ff_initialize` → `sd_ff_batch::prepare` → `sd_worker::ff_batch` → `sd_ff_batch::execute` → `sd_batch::run_entries`です。FF用の計画では全エントリーの入力サイズを0とし、実ファイルを開かない空のメモリーストリームから期待値全体を`0xFF`として生成します。単発APIの`sd_fill`/`sd_verify_fill`はこの経路では使用しません。PC上の入力ファイル、`output`の作成・削除・書き換えは行いません。

模擬SDテストでは、先頭32KiB・全フラグ・CSV順・終端、現行CSV全94領域、無効計画、複数チャンク、非整列領域、対象外と隙間の保持、書込失敗・読込失敗・未更新読込バッファ・直後照合不一致・最終照合不一致を確認します。画面処理テストでは、入力一致ファイル0件でも実行できること、操作制限、古い進捗の除外、最終照合前に完了としないこと、最終照合失敗・事前検査失敗時の結果保持を確認します。

実機でのUAC、ボリュームロック、先頭領域を書き換えた後のWindowsと機器側の認識・抜去時の挙動は未検証です。

## 11. ts-sddirectとの比較調査

同日、追加された`C:\Users\SYSTEM-PC7\source\repos\electron3\ts-sddirect`も調査しました。**現在のソースと付属CSVでは、先頭32KiBもFF書き込みの対象です。**

処理経路は以下です。

```text
resources/data/sdDirectaxs.csv
  → loadSdDirectInfoMap()（A行を取り込む）
  → onMenuSdClear()（マップの全エントリーを処理）
  → parseAddressInfo()（終了 − 開始 ＋ 1）
  → window.api.sdAccess.fill(driveLetter, startAddress, size, 0xFF)
  → backendAPI.sdFill → POST /api/sdFill
  → ts-sdservice の sd_fill_handler
  → windows_api::sd_fill（PhysicalDriveを指定位置へシークして書込）
```

CSVの先頭行は次のとおりです。

```csv
A,FILE-00.001,00000000,00007FFF
```

この行は`A`なのでマップへ入り、開始アドレス`0`・サイズ`32,768`・埋め値`255`でサービスへ渡されます。画面・preload・調査したサービスのどの段階にも、先頭32KiBをスキップしたり別のアドレスへ補正したりする処理はありません。書込が成功すれば先頭32KiBがFF化され、そこにある管理情報も上書きされます。

確認箇所：

- `ts-sddirect/resources/data/sdDirectaxs.csv:1`：対象行。
- `ts-sddirect/src/renderer/src/utils/csvUtils.ts:21–57`：`A`行のみをマップへ登録。
- `ts-sddirect/src/renderer/src/pages/Home.vue:573–633`：全エントリーへのFF書込と直後照合。`ALLVIEW.vue:555–612`にも同じ処理あり。
- `ts-sddirect/src/renderer/src/utils/sdOperationUtils.ts:26–61`：アドレス解析と領域サイズ計算。
- `ts-sddirect/src/preload/index.ts:117–130, 180–189`：アドレス・サイズを変えずHTTPへ転送。
- `ts-sddirect/src/main/index.ts:1624–1631`：開発時はプロジェクト内、配布時は`app.asar.unpacked`内のリソースCSVを読み込む。
- `ts-sdservice/src/main.rs:243–251`：受信したアドレス・サイズをそのままFF書込関数へ渡す。
- `ts-sdservice/src/windows_api.rs:196–308`：物理ドライブの指定アドレスへシークし、指定値で書き込む。

移植元SDDirectAXSとはフラグの扱いが異なり、`ts-sddirect`はCSVの`A`行だけがマップに入ります。付属CSVでは`E`前に`A`行が108件、合計45,633,024バイトあり、先頭の`FILE-00.001`もその中に含まれます。

この結果はソースと付属CSVの確認です。インストール済みexe・サービスのバージョンや配布先CSVの内容、実際のSDが書き換え済みかどうかは確認していません。対象プロジェクトのコード変更や実機の初期化は行っていません。
