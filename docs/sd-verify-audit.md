# SD書込・ベリファイ調査

調査日：2026-10-26。対象は `SD書込` → `run_sd_write` → `sd_worker::write_batch` → `sd_batch::execute` の経路。実機の故障SDは操作せず、コード確認・Windows公式資料・模擬故障テストで調査した。初回調査後、書込・SD読込・期待値の3バッファ分離と、照合前の読込先のビット反転初期化を実装した。以下では改修前の再現と現在の動作を区別する。

## 結論

書込後にSDを読み戻し、期待値との全バイト比較を実行している。期待値と読込値を同じ配列同士で比較する不具合は確認していない。初回調査時点では書込用／SD読込用のメモリーを共用していたが、現在は書込・SD読込・期待値を完全に独立した3バッファへ分離している。

初回調査で最も重要だった不足は、全ファイル書込後の最終再照合がないこと。後続の書込が照合済みの領域を破壊する故障を見逃すことを再現した。現在は直後照合を維持した上で全対象の最終再照合を追加し、同じ模擬故障を正常完了前に検出している。

現在の正常完了は「各対象領域が書込直後の照合に成功し、全書込後の最終照合でも期待値と一致した」という意味。カード全容量、電源断後の保持、認識の安定性、容量表示の真偽を保証するものではない。今回のカードでどの故障が起きているかは、この調査だけでは断定できない。

## バッファと比較処理

`src-tauri/src/sd_batch.rs` の `execute` から呼ぶ `run_entries` は以下の独立した3領域を確保する。

| バッファ | サイズ | 用途 |
| --- | --- | --- |
| `write_buffer` | 4MiB + 64KiB | 書込データの生成とSD書込専用 |
| `read_buffer` | 4MiB + 64KiB | SD読込専用。非整列領域の隣接バイト保持のための事前読込にも使用 |
| `compare` | 4MiB | 照合時に入力ファイルを再読込して作成する期待値 |

`transfer_phases` は、各ファイルの領域全体の書込 → `FlushFileBuffers` → 領域全体の読込・直後照合を行う。全ファイルに対する処理後、同じ比較処理を読込専用で再実行して全対象を最終照合する。照合時は必ず `disk.read` を呼び、SD読込値 `payload` と、独立した `compare` を1バイトずつ比較する。チェックサムの一部比較やサンプリングではない。

照合の各チャンクで期待値を生成した後、SD読込先の対象部分を期待値のビット反転値で埋めてから読む。読込先が未更新なら必ず期待値と異なる。書込用バッファをSD読込先に渡すことはなく、必要な隣接バイトはSD読込用バッファから書込用バッファへコピーする。

短いファイルの末尾は `0xFF` を期待値に含める。0バイトのファイルは領域全体を `0xFF` として照合する。大きいファイルはCSV領域サイズまでを対象とする。入力ファイルは処理中、書込・削除の共有を許可せず開いている。

`windows_api::BatchDisk::read` は `ReadFile` の成否と返却バイト数を確認し、失敗・不足なら正常扱いしない。`write` と `flush` もエラーを伝播する。`file_done` は直後照合成功後、`final_file_done` は最終照合成功後、`done` は全対象の最終照合とSDハンドルの解放後にのみ通知される。最終照合失敗は `final_failed` として通知し、正常完了と混同しない。

## 再現した不足と限界

### 1. 後続ファイルによる照合済み領域の破壊を見逃す

2つの異なる論理アドレスが同じ保存場所に対応する模擬ディスクで、次を再現した。

1. アドレス0へ `0xA1` を512バイト書込 → 直後の照合に成功。
2. アドレス512へ `0xB2` を512バイト書込 → 直後の照合に成功。
3. アドレス0を再読込すると、期待していた `0xA1` ではなく `0xB2` になっている。

改修前は直後照合だけだったため、この2領域がともに成功扱いになった。現在は `run_entries` の最終照合でアドレス0の不一致を検出し、失敗ファイル名・不一致アドレスを報告して停止する。これは容量の偽装・アドレスの折返し等をモデル化した再現であり、今回の実カードに同じ故障があると確認したものではない。

### 2. 読込が成功を偽ってバッファを更新しない場合、残った書込データで一致する

改修前は、書込と読込をともに実行せず、成功だけ返す意図的に不正な模擬I/Oで、512バイトのセクター境界に揃った書込が照合成功になった。共用 `io` に残る書込データと期待値が一致するため。現在は3バッファ分離と読込先のビット反転初期化により、このケースは照合不一致として検出する。期待値が `0x00`・`0xFF`・`0xA5` の場合と、読込先の半分しか更新しない場合もテストで検出を確認している。

これは読込APIの契約違反を仮定した防御上の弱点。通常のSD読込エラーや、返却バイト数が0／不足の場合は実Windowsバックエンドで検出される。「正常な `ReadFile` でも共用バッファだから必ず誤判定する」という意味ではない。今回そのようなドライバー応答があった証拠もない。

### 3. 書込前から同じ内容なら、書込無視と正常な再書込を区別できない

以前から `0x33` の領域に `0x33` を書込むテストでは、書込を無視する模擬ディスクも照合成功になった。これは読込値が正しくても生じる。通常のベリファイは内容一致を確認する処理なので、同一内容での繰り返し成功だけでは、カードに新しい内容を保存できることを証明できない。

### 4. 検査範囲と保存期間が限定される

CSVで定義され、対応ファイルのある対象領域だけを検査する。対象外領域の不良、カード全容量の異常、照合後に発生する破損、抜き差し・電源断後の保持は未検査。認識不良が断続的に発生するカードでも、今回の処理中に認識できて対象領域が一致すれば完了し得る。

## Windowsキャッシュの確認

物理ディスクは `FILE_FLAG_NO_BUFFERING` で開き、書込後に `FlushFileBuffers` を実行している。Windowsの通常のデータキャッシュだけを読み戻して一致している、という実装ではない。

一方、`FILE_FLAG_NO_BUFFERING` が制御するのはシステムキャッシュであり、機器内のハードウェアキャッシュとは別。Windows公式資料もその区別を明記している。`FILE_FLAG_WRITE_THROUGH` は現在の一括書込ハンドルには指定していないが、追加しても機器側の対応に依存するため、電源断後の保持をアプリだけで断定することはできない。

- [Microsoft：File buffering](https://learn.microsoft.com/en-us/windows/win32/fileio/file-buffering)
- [Microsoft：CreateFileW（キャッシュ関連フラグ）](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
- [Microsoft：FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)

## 追加した調査テスト

`src-tauri/src/sd_batch.rs` の `audit_` で始まる6テスト。実際の `transfer` に模擬ディスクを注入する。全読込範囲のテストでは、隣接バイト保持の事前読込も含めてSD読込先と書込元のメモリー範囲が重ならないことも確認する。未解消の故障の見逃しを記録するテストは、現状の不足を再現する特性テストであり、望ましい仕様として承認するものではない。

| テスト | 確認結果 |
| --- | --- |
| 全チャンクの読込範囲とflush後の順序 | 4MiBを跨ぐ非整列領域の全対象バイトを読込・照合 |
| 先頭・チャンク境界前後・末尾の1バイト破損 | `0xFF` 補完部を含め、不一致の正確なアドレスを検出 |
| 読込／書込／flushの失敗、書込の無視 | エラーまたは照合不一致として停止 |
| ファイル間のアドレス別名化 | 直後照合だけでは見逃す破損を再現。追加した最終照合テストでは正常完了前に検出 |
| 読込成功を偽り格納先を更新しない／一部だけ更新するI/O | 改修前の見逃しを解消し、現在は照合不一致を検出（API契約違反の仮定） |
| 書込前と同じ内容での書込無視 | 読込比較だけでは新規保存の実行を区別できないことを再現 |

実行コマンド：`cargo test --manifest-path src-tauri/Cargo.toml --lib --offline`。

## 修正・追加検証の優先順位

1. **実装済み：全書込後に全対象を最終再照合する。** 直後照合を維持し、最終再照合の完了を正常完了の条件にした。アドレス別名化の失敗ケースと、正常時に追加書込をせず全対象を読込むケースをテストで確認する。
2. **実装済み：書込・SD読込・期待値を独立したバッファにする。** 読込先を期待値の各ビットを反転した値で事前に埋め、読み込まれていない部分が残るケースを検出する。固定の0埋めだけでは期待値が0の領域に弱いため採用しない。
3. **抜き差し後の読込専用ベリファイを追加する。** 電源断後にも対象内容が保持されるかを、再書込せず確認する。
4. **カード診断は別機能として扱う。** 真の容量や書込能力の検査には異なるパターンで広い範囲を検査する必要があり、対象外データを破壊するため通常のSD書込に自動追加しない。
